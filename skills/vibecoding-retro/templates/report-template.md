# 报告模板

**目标读者是没读过这个工具文档的人。** 他扫一眼就该知道:这次哪儿亏了、亏了多少、下次怎么办。

---

## 格式

```markdown
# 复盘 · <项目或任务一句话>(<日期>,<N> 轮)

<一句话总评。好就说好,不用硬找问题。>

## 这次的账

<3–5 个数字,人话写。不要贴大表格。>
例:27 轮,活跃 6.8 小时,缓存命中 95%(很好,大部分上下文没重复付费)。

## 发现 N 个可以改的地方

### 1. <一句话说清现象,不用术语>

<证据:第几轮、哪句话。可以引用原文。>

**代价**:<能算就给数字,算不出就说具体后果>

**下次**:<一个今天就能做的动作 + 下次看什么数据判断它生效了>

### 2. …

### 3. …

## 上次说的那件事

<只在有可验证内容时才写这一段。一两句话说结论,有数字就给数字。>
<没有可验证的就整段省略,不要留空标题。>

## 安全提醒

<只在检出疑似密钥时才写。说类型、第几轮、是你贴的还是助手复述的。>
<绝不复述任何密钥字符。拿不准的说"看着像,你确认一下"。>
```

## 写之前对一遍

- [ ] 通篇搜一下:有没有字母编号(KB-01、T1、J4)、档位缩写(L 档、M 档)、分类学名词(问题定义缺口、委托校准)?**有就改成人话**
- [ ] 每条问题是不是都有**现象、代价、怎么改**三段?
- [ ] 每条能不能指到**具体轮次**?指不到就删掉
- [ ] 是不是 **≤3 条**?
- [ ] 估算出来的数字有没有带"**约**"?
- [ ] 有没有把 token 换算成**美元**?(不许)
- [ ] 有没有给出这个工具范围之外的建议(产品规划、职业发展、要不要做某个功能)?**删掉**
- [ ] 数据有不可靠的部分(`schema_health.degraded` 非空),有没有说明?

## 几件容易做错的事

**别为了凑数硬找问题。** 这次干得好就说"这次没什么可改的,以下几点做得对:…"。一份诚实的空报告比三条勉强的建议有价值。

**别把好行为漏掉。** 缓存命中率高、动手前先要方案、对 AI 的分析提出了正确反驳——这些看到了就写一句。只挑毛病的工具没人愿意用第二次。

**代价要说人话。** 不是"消耗了 9114K 计费 input token",是"这段花了 910 万 token,而它改的是一个核心机制还不存在的东西"。

**别解释工具自己的机制。** 用户不需要知道什么是基线、多少条记录才能出数、什么是台账。这些一律不出现在报告里。
