# 浪费模式:检测标准与阈值

这份是**机械可测**的部分,判定不靠语义理解。阈值直接改数字即可。

脚本侧已经实现的阈值在 `scripts/parse_session.py` 顶部;这里是**怎么解读、怎么写进报告**。

## 报告里怎么说数字

`parse_session.py` 的输出里有 `metric_confidence`,把每个指标标了三级:

| 级别 | 含义 | 报告里怎么写 |
|---|---|---|
| `exact` | 来自 API 返回或直接计数 | 直接当事实说 |
| `derived` | 由精确值按明确规则推算 | 可以说,但要带一句口径 |
| `estimated` | 含粗略换算(比如按字符数除以 4 估 token,中文误差可达数倍) | **必须带"约"**,且不能只靠它支撑一条结论 |

**任何情况下不把 token 换算成美元。** 订阅制下那是估算的估算,还要维护一张会过期的价目表。只说 token 数量和倍数。

`schema_health.degraded` 非空时,报告里要说明哪部分数据不可靠——**说错数字比不说更伤**。

## 检测项

| 现象 | 判定 | 怎么写进报告 |
|---|---|---|
| **重复读同一文件** | 同一路径被 Read ≥3 次 | 点名文件和次数。注意:跨天的长会话或压缩之后重读是正常的,证据偏弱,别当主要问题说 |
| **单个工具结果过大** | 字符数 / 4 估算 ≥ 10000 | 说"第 N 轮有一个约 XX 万 token 的结果进了上下文"。**带"约"** |
| **上下文拖拽** | 见 `carry_cost`:大块内容进来后被后续多少次请求反复携带 | 这是"当时那一下"之外的持续代价。也是估算,带"约" |
| **缓存命中率低** | `cache_read / (input + cache_read + cache_write) < 50%` 且会话超过 10 轮 | 命中率高(>90%)要在报告里正面说一句——这是做得好的地方 |
| **上下文压缩** | `compact_events > 0` | 压缩本身不是错,但要看**压缩之后有没有出问题**(记混、重复问已经说过的事)。有,才值得写 |
| **上下文持续高位** | 会话后半程每轮计费 input 持续很高,且任务本可拆分 | 结合"一个会话装了太多事"一起说 |
| **方向性返工** | 因方向错误推倒重来的轮次占比 > 25% | 用逐轮账单算出那段的 token |

## 任务规模(内部用,不出现在报告里)

只用于和个人历史做同类比较,**不要在报告里说"这是 L 档任务"**——对用户没有信息量。需要提及时说"这种规模的任务"。

- **小**:改配置、修 typo、写单个函数、回答问题。通常 ≤10 轮
- **中**:一个完整功能、跨 2–5 个文件的重构、调一个 bug。通常 10–30 轮
- **大**:新模块、架构调整、涉及 5 个以上文件或需要设计决策。通常 30 轮以上

写进档案记录的 `scale` 字段,供 `compare` 做同类比较。

## 和个人历史比

```bash
python3 scripts/ledger.py compare --session-json <解析结果.json> --scale 中
```

- **`ready:false`(同规模记录不足 10 条)→ 报告里不要提"超标"。** 没有分母就没有超标。新用户前十几次都会是这个状态,这是正常的,不用道歉,也不用解释机制
- `flagged` 里的指标 → **回到 `prompts[]` 找出是哪一轮造成的**。偏差只负责开启调查,不负责下结论。找不到具体行为原因就不要写进报告
- 只说倍数("用了你平时的 2.3 倍"),不说美元

## 密钥泄漏

`secret_leaks` 非空时**单独提醒**,不占问题名额,也不算"效率问题":

- 按类型、轮次、来源说明(是你贴的,还是助手复述的——助手的思考过程也是明文写在本地日志里的)
- **绝不复述任何密钥字符**。解析脚本已经把命中处替换成 `«已隐去:…»`,原样保留,不要还原也不要猜
- 说明覆盖范围:不扫工具执行结果
- 误报是有的(比如代码里的示例常量)。拿不准就说"看着像,你确认一下",不要吓唬人
