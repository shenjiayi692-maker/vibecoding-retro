# 能力诊断规则(产品核心)

本 skill 的核心价值:从会话数据中发现用户在"成为 AI 产品经理"路上的能力缺口。效率评分只是证据基底,诊断才是正文。

## 总原则

1. **假设,不是断言**。从聊天记录推断思维缺陷本质是推测。每条诊断措辞为"这里可能反映出 X,你觉得是这样吗?",由用户确认或否决,反馈写入台账
2. **证据强制**。每条诊断必须引用本次会话的具体位置(第几轮、哪句话、哪次返工),没有证据的诊断禁止输出
3. **每次最多 2 条**。诊断过载 = 复盘疲劳 = 产品死亡
4. **优先级序**。多个信号同时命中且证据强度相当时,按此序出场:**T1 问题定义 > T2 验收标准 > T4 假设外显化 > T6 委托校准 > T3 范围控制 > T5 抽象层级 > J2 方案评估 > J3 验证行为 > J1 词汇缺口**。前四项是 PM 成长的主干,是本产品的重点;J1 不占用诊断名额,缺词直接记 missing_terms 走台账累积。证据强度差距明显时,强证据优先于序位

   **J4 是例外,不在上面的序列里**(v2.5 修订,依据:实测中 J4 是单次复盘里价值最高的一条)。J4 一旦经台账 diff 确认成立——同一个坑跨 ≥2 次会话重现——它的证据就不是单次推测,而是**有历史记录为凭的最强一档**,此时按"强证据优先"原则**优先出场并占用诊断名额**。理由:其余九项都在回答"这次你做得怎样",只有 J4 回答"你有没有在变好",而重复踩坑不沉淀本身比任何单次失误都更贵。反过来,diff 无重合时 J4 不得输出——它没有"弱证据"形态
5. **单次是信号,累积才是结论**。诊断先进台账;同一缺口第 3 次出现才升级为"结构性缺口",此时给学习建议(读什么/练什么),而非工作流建议

## 思维架构类缺口(PM 核心能力)

逐条检查以下信号。检测方法基于:用户消息文本、返工模式、会话走向。

### T1 问题定义(problem framing)
- **信号**:首条 prompt 直接给解决方案("用 X 技术实现 Y 功能"),中途因"真实需求不是那个"而推翻;或 Claude 反问"你想解决什么问题"后方向才清晰
- **典型话术特征**:首条以"帮我用/写一个/实现"开头且全篇无一句"为什么/用来解决什么";中途出现"其实我真正想要的是"、"等等,我想做的不是这个"、"换个思路,我的目的是"——这三类话术是 T1 最强证据,出现即可引用
- **区分**:中途基于新信息的合理转向不算(比如试了发现技术不可行);只有"需求本身从一开始就没想清"才算
- **为什么关键**:跳过问题定义直奔方案,是 PM 最致命的习惯
- **结构性缺口的学习建议方向**:问题定义框架(JTBD、5 Whys)、《The Mom Test》

### T2 验收标准思维(definition of done)
- **信号**:会话开始时说不出"怎么算做对了";靠"看起来行了"收尾;需求是看到输出之后才被"发现"的
- **典型话术特征**:正向信号(好)——首条含"完成的标准是"、"要能通过 X 测试"、"至少要支持 A/B/C 三种情况";负向信号——收尾只有"行,差不多了"、"看起来可以";强证据——看到结果后说"哦我还需要它能……"且该需求明显属于任务本体而非新想法
- **区分**:探索性/原型任务允许边看边定义,不扣;交付性任务才检此项
- **学习建议方向**:验收标准写作、Given-When-Then 格式练习

### T3 范围控制(scope discipline)
- **信号**:会话中途 ≥2 次"顺便再加个……";单会话混入多个不相关目标;成品比最初描述大一圈
- **学习建议方向**:MVP 切分练习、写 out-of-scope 清单的习惯

### T4 假设外显化(assumption surfacing)
- **信号**:返工源于用户脑中有个没说出口的前提,Claude 按另一种理解填空了。这类纠偏消息一数就知道
- **典型话术特征**:"哦对了,忘了说……"、"我以为你知道"、"不是那个意思,我们的用户是……"、"默认应该是 X 啊"。统计方法:通读用户消息,凡属"补充一个开工前就已存在于用户脑中的前提"即计一次,≥2 次为强证据
- **常见隐含前提清单**(帮助识别):目标用户/市场、运行平台、数据格式与规模、语言(中/英文输出)、已有代码约定、性能与预算约束
- **学习建议方向**:PRD 中的 assumptions 段写作、prompt 前置约束清单

### T5 抽象层级切换(zoom in/out)
- **信号**:在实现细节里死磕 >15 轮,最终靠退回架构/需求层换方案解决——说明卡住时缺少"上升一层"的本能
- **典型话术特征**:死磕段的特征是连续多轮"还是不行"、"再试试 X"、"改成 Y 呢"(同层穷举);解困话术是"要不换个方案"、"我们退一步"、"其实可以不用这个做法"——若解困话术由 Claude 而非用户提出,证据更强(说明用户自己没有这个本能)
- **正向信号(记入好行为)**:卡住 3–5 轮内用户主动说"退一步想"或主动要求重新评估方案
- **学习建议方向**:第一性原理拆解练习、卡住时的"上升一层"检查清单

### T6 委托校准(delegation calibration)——唯一同时打分的能力项
- **信号(过度委托)**:把该留在人这边的判断推给 AI——"你觉得该做哪个功能"、"优先级你定"、"你决定吧"用在产品取舍上;对 AI 给出的取舍方案零质疑照单全收。判断类决策包括:做什么/不做什么、为谁做、先做哪个、接受什么代价
- **信号(委托不足)**:AI 擅长的机械活自己手工干——用户说"我自己手动改了 X"、"我一个个查过了"而 X 属于样板代码/语法检查/格式校对这类 AI 本可自查的工作
- **为什么是第一能力**:知道人机边界在哪,正在变成 AI 时代 PM 的核心素养,而 vibecoding 会话恰好是这个能力的最佳观测场——这也是本产品独有、现有工具都没有的指标
- **打分**(1–5,计入评分卡第五行):判断类决策自己拿主意且给出理由、执行类工作充分交给 AI → 5;各有一两处错位 → 3–4;系统性倒置(判断外包、执行手工)→ 1–2
- **为什么单独打分**:人机边界感是 AI 时代 PM 的第一能力,且判据相对客观
- **学习建议方向**:决策权矩阵——哪些决策必须留在人这边

## 技术类缺口

### J1 概念词汇缺口(vocabulary gap)
- **信号**:绕圈描述有标准名称的东西("那种服务器主动推给我的机制" = webhook;分不清该叫 webhook 还是轮询);用词模糊直接推高 prompt 模糊度和迭代次数
- **检测方法**:通读用户消息,凡"用一句功能描述代替一个标准术语"即捕获,把对应的标准术语记入 missing_terms。注意同时记录该词所属领域(API 通信/数据库/前端状态/部署运维/安全认证等)以便聚类
- **特殊处理**:把缺的词记进台账的 `missing_terms` 列表。台账里同领域词汇 ≥3 个时聚类,输出"你该系统补一下 X 领域"(如:API 通信、数据库、前端状态管理)

### J2 方案评估能力(technical judgment)
- **信号**:对 Claude 第一版技术选型零质疑全盘接受,后来发生架构级返工——说明接受当时没有能力挑战它
- **典型话术特征**:选型时刻用户只回"好/可以/就这样";全程未出现"为什么选这个"、"有没有别的方案"、"代价是什么"、"数据量大了会怎样"任何一句,且后续发生架构级返工 → 强证据。若问过但仍返工,不算此项(那是信息不足,不是能力缺口)
- **学习建议方向**:学会三个万能追问:trade-off 是什么、规模变大后会怎样、最简方案是什么

### J3 验证行为(verification habit)
- **信号**:diff 没看就接受,bug 后置爆发
- **典型话术特征**:改动刚给出用户立刻回"继续/下一个"(间隔极短、无任何针对内容的评论);多轮之后集中出现"怎么全坏了"、"之前哪一步改错了"式的回溯排查 → 两者同时出现为强证据。正向信号:每个改动后有"我看了,X 处没问题"或要求跑一下再继续
- **学习建议方向**:每轮结束的 30 秒验证习惯、让 AI 自己写验证步骤

### J4 知识沉淀率(knowledge capture)
- **信号**:对照台账,连续 ≥2 次 session 踩同一个坑(同类报错、同类误解、同类纠偏)而没有沉淀为 CLAUDE.md 规则/笔记/可复用 skill——重复踩坑而不沉淀,本身就是缺口
- **检测方法**:每次复盘结束把本次的坑(waste_flags、纠偏主题)写入档案;下次复盘时先 diff 本次的坑与历史的坑,重合即触发。同时检查:上次报告建议沉淀的规则,这次会话里生效了吗(同类问题是否消失)
- **这一条只能跨会话检测**,单次会话不输出
- **diff 必须真做**,不能凭印象:跑 `scripts/trend_report.py --last 10`,拿 `series[].waste_flags` 和 `waste_flag_counts` 与本次的坑逐项比对,证据里写明"这是第 N 次出现"。命中即按总原则 4 的例外条款优先出场

## 缺口台账(gap ledger)

文件:`~/.claude/vibecoding-retro/gap-ledger.json`

```json
{
  "gaps": {
    "T1": {"count": 2, "dates": ["2026-07-10", "2026-07-15"], "user_confirmed": 2, "user_rejected": 0, "status": "watching"},
    "J1": {"count": 1, "missing_terms": ["webhook", "idempotency"], "status": "watching"}
  },
  "graduated": {
    "T3": {"resolved_date": "2026-07-01", "note": "连续5次无scope creep信号"}
  }
}
```

规则:
- `count` 只累计**用户确认**的诊断;被否决的记入 `user_rejected`,同一缺口被否决 2 次后停止检测该项(可能是误判模式)
- `count >= 3` → `status: "structural"`,报告中升级呈现并给学习建议
- structural 缺口连续 5 次 session 未再出现 → 移入 `graduated`,报告中庆祝("范围控制已毕业🎓")——**看见成长和看见缺口同样重要**
- 学习建议给方向和一个具体起点(一本书/一个练习/一个习惯),不开长书单

## 诊断的证据分级

写诊断时自评证据强度,弱证据宁可不说:

- **强**:有明确的返工/纠偏消息直接对应(可引用原话)
- **中**:模式推断(轮次分布、时长占比)
- **弱**:单一间接信号 → 不输出,只默默记入台账的观察备注
